The whole project in four sentences. AI coding agents delete code whose purpose they can’t see — a check, a retry, a lock. The reason a line exists is almost always written down in a commit message or a bug ticket, but the standard tool for finding it, git blame, usually points at a reformat instead. We built a system that traces any line past reformats, renames and moves to the change that really created it, attaches the ticket that explains it, and serves all of that to AI agents through a standard protocol. On a frozen, held-out test set it finds the right commit 83.5% of the time, against 69.2% for git’s strongest settings. And in a controlled pilot, an AI agent given the tool kept a historically important check in 22 of 32 runs, against 16 of 32 without it.

01The problem, from zero

Every piece of software is built from thousands of small changes called commits, stored in a system called git. Each commit carries a message saying what it did and why — “Fixed #31375: make_password() must accept only bytes or strings”. Projects also keep tickets (bug reports and discussions). Together, this history is a diary of every decision in the codebase.

When you want to know why a line of code exists, you ask git blame, which names the last commit that touched that line. And that is the problem: the last commit that touched a line is very often one that just reformatted the file, renamed a variable, or moved code around — a change that altered how the code looks but not what it does. The real reason is buried several layers deeper.

A real example from Django

Line 114 of django/contrib/auth/hashers.py is part of a deliberate type check in the function that hashes passwords:

if not isinstance(password, (bytes, str)):
    raise TypeError(
        "Password must be a string or bytes, got %s." % type(password).__qualname__
    )

Ask git’s strongest settings (git blame -w -M -C -C) about that line and the answer is a 2022 commit: “Refs #33476 — Reformatted code with Black.” Only the layout changed. The behaviour actually comes from a 2020 commit: “Fixed #31375 — Made make_password() accept only bytes or strings” — a deliberate guard against weak passwords, with a ticket explaining the risk.

Why this matters now. Millions of developers merge code written by AI agents every day. An agent that reads “Reformatted code with Black” learns nothing — deleting the check looks like harmless clean-up. An agent that reads “accept only bytes or strings, see ticket #31375” knows the line is a guard, and keeps it or asks first. The quality of that one answer decides whether AI-assisted coding quietly erodes the protections in our software.

How common is the problem? Under git’s strongest settings, 22.7% of lines in sampled Django files land on a commit that Django’s own developers list as pure formatting. For over a quarter of Django’s behaviour-carrying lines, our method and git’s best answer disagree about where the line came from.

02What the system does today

Provenance is a working command-line tool, web app and agent server. Preparing a repository takes three commands and a few minutes:

# one-time setup per repository
uv run provenance clone django      # download its full history
uv run provenance ingest django     # load 35,104 commits into a local database
uv run provenance classify django   # find every cosmetic change — 5.2 min on an M1 Air
uv run provenance link django       # connect commits to tickets, reverts, backports
uv run provenance fetch-tickets django   # politely download the tickets, 1 request/second

Then you can ask questions:

uv run provenance why django django/contrib/auth/hashers.py 114
# → the chain of commits, reformats marked and skipped, ticket links attached

uv run provenance explain django django/contrib/auth/hashers.py 112 115
# → "This code was added in commit 8aa71f4e87 to resolve Ticket #31375 by
#    restricting make_password() to only accept bytes or str arguments…"
#    Confidence: high · citations: [commit 8aa71f4e87] [Ticket #31375]

uv run provenance search django password bytes
# → full-text search across 17,178 locally stored Trac tickets

uv run provenance ui        # the web interface, on your own machine
uv run provenance mcp django  # the server AI agents connect to

03How tracing works: three layers

We don’t replace git blame — git’s line-matching is fast and battle-tested. Instead we tell it which commits to skip, and then step through the ones it can’t skip. Imagine one line’s history, newest first:

YearWhat the commit didKindWhat we do
2022Black reformats the whole filecosmeticSkip (Layer B)
2020Renames a variable across the filerenameSkip (Layer B)
2018Fixes a bug elsewhere, re-wraps our linemixedStep through (Layer C)
2015Adds the check — the real answerlogicStop here

Layer A — classify

Once per repository, parse every version of every changed file and ask: did the meaning change, or only the look? Each file-change gets a label: cosmetic, rename, move or logic. This is per file, not per commit — a commit that reformats one file and fixes another is skipped only for the first.

Layer B — skip

Give git blame each file’s list of cosmetic commits through its --ignore-revs-file option — the same mechanism Django’s developers feed by hand. Git then looks straight through the reformats.

Layer C — step

Some commits mix a reformat with a real fix and can’t be skipped whole. For the one line we care about, Layer C reads the commit’s diff: if the same tokens were just re-arranged, step to the older version and keep blaming; if the line was genuinely edited, record a logic change and continue. The tracer reports two answers — the last logic change and the first appearance — because “why” can live in either.

The safety rule: when unsure, call it logic. The two possible mistakes don’t cost the same. Wrongly skipping a commit hides the line’s true origin; wrongly keeping it just gives git’s ordinary answer. So unparsable files, unknown languages and unclear cases all count as logic. Every real bug found in development was in the dangerous direction — a real change that looked cosmetic — and each one is now a permanent test.

04Layer A up close: proving a change is only cosmetic

The trick: turn the code into a stream of meaningful tokens, dropping everything that can’t affect behaviour. If the stream is identical before and after a change, the change cannot have altered what the code does. These two versions differ in text but produce the same stream:

# before (2020)                              # after Black (2022)
raise TypeError(                             raise TypeError(
    'Password must be … %s.'                     "Password must be … %s." % type(…)
    % type(…)                                )
)
Ignored — can’t change behaviourKept — can
Whitespace, line wrapping, blank linesAny change to the real tokens
Comments; docstrings without doctestsPython indentation that moves code into or out of a block
Quote style, string prefixes, adjacent strings joinedWhere one statement ends and the next begins
Trailing commas, redundant bracketsDocstrings containing >>> — those run as tests
Import order within a blockBrackets that change meaning

A rename is accepted only when names are swapped consistently and every changed name is defined in that file — the second rule stopped a library swap (base64.encodestring → b64encode) from passing as a rename. A move means the same code appears elsewhere unchanged. Everything else, including anything we can’t parse, is logic.

How do we know Layer A is right without any human labels? Python ships its own parser. If the syntax trees before and after a change are equal, the change almost certainly kept the behaviour — a second opinion that shares none of our code. Across 74,840 Django file changes, 99.91% of the changes we call cosmetic have identical trees.

05Tickets, search and the link graph

A commit sha alone doesn’t explain anything to a person. The explanation lives in the ticket the commit references. So the system builds a link graph from commit messages: in Django, “Fixed #31375” links the commit to Trac ticket 31375; in Redis, “(#1987)” at the end of a subject names the pull request that merged it. It also tracks reverts and backports — if a commit was later reverted, every answer says so, because that changes its meaning.

  • 21,215 Django commits are linked to tickets, and 4,638 Redis commits to pull requests.
  • The ~17,200 linked Trac tickets are downloaded by a polite crawler: one request per second, a descriptive user-agent, each ticket fetched once, resumable. Titles and descriptions are stored locally.
  • Everything is searchable: an FTS5 full-text index answers provenance search django password bytes instantly, offline.

06Explanations that cite their sources, or abstain

The newest stage turns evidence into a short, plain-English answer. For a line (or a block of up to 40 lines), the system traces it, gathers the commit messages and ticket text behind the logic commits, and asks Gemini to write two to four sentences — under strict rules:

  • Only the evidence given. The model sees the gathered messages and tickets, nothing else, and may not guess from the code alone.
  • Every claim must cite. Answers carry citations like [E1], each resolving to a specific commit or ticket. An answer whose citations don’t check out is discarded.
  • Weak evidence means abstaining. If the history doesn’t say why the code exists, the system says exactly that, rather than inventing a story. For a tool meant to stop agents making confident mistakes, a trustworthy “I don’t know” is a feature.
  • Quoted text is data. Ticket and commit text is fenced in the prompt as untrusted material written by strangers, so text in a commit message can’t steer the model.
  • Replies are cached in the local database: repeating a question is free, demos work offline, and the report can show the exact reply behind every explanation.

Real output for the password-check block (hashers.py lines 112–115): “This code was added in commit 8aa71f4e87 to resolve Ticket #31375 by restricting make_password() to only accept bytes or str arguments. Previously, the function accepted almost any Python object due to automatic casting, which created a potential security risk of programmers accidentally generating weak passwords…” — confidence high, citing the commit and the ticket, both clickable.

07How an AI agent uses it

MCP (Model Context Protocol) is the standard way AI applications discover and call outside tools — one server works with Claude Code, Cursor and others. Registering takes one line:

claude mcp add provenance -- uv run provenance mcp django

The agent gets two tools: why_line and why_range. Told to “simplify make_password()”, a connected agent can ask why line 114 exists before touching it, and receives the traced chain, the linked tickets with excerpts, and the commit messages. Safety is designed in:

  • Read-only. The tools can’t edit files or run commands, and paths are validated so the server can’t be used to read outside the repository.
  • Untrusted by default. Commit messages and ticket text arrive in fields explicitly marked untrusted — anyone can write a commit message, including one that says “ignore your instructions”. The agent is told to treat them as data.
  • It never says “safe”. Finding no history only means none was found, and every reply says so.
  • Evidence, not prose. The calling agent has its own powerful model; our server hands it facts to reason over.

10How we measured accuracy, honestly

Charts of “our answer differs from git’s” don’t prove we’re right. For that, someone must determine the true answer for a sample of lines — a gold set — and score every method against it. Our protocol, in order:

  1. Tune on a development set. 60 lines were sampled from Django and Redis (stratified: oversampling lines where methods disagree, then weighted back), labelled blind, and used to find and fix failure patterns.
  2. Freeze the method. After the fixes, the code was frozen in one commit. No rule has changed since.
  3. Draw a fresh test set. 60 new lines, excluding every development line, drawn only after the freeze — so the test could not influence the method.
  4. Score once. The frozen method ran on the test set exactly one time. That number is the headline.

Who labelled, and why that’s stated everywhere

The labels are AI labels. Claude labelled every line using only git’s own history; Gemini — a different vendor’s model — labelled the same lines blind, never seeing Claude’s labels or any method’s answers. First-round agreement was 86.7% on the test set (Cohen’s kappa 0.86); after a structured adjudication round showing both candidates with evidence, the two models agreed on 60 of 60 test lines. No human has labelled the gold set — one person could not blind-label 120 lines and build the system in the same two weeks — and the report says so wherever the numbers appear. Every label, both models’ raw replies, and all disagreements are committed for anyone to audit.

The comparison is deliberately fair: we score against git’s strongest settings and Django’s hand-kept list, not just plain blame, with bootstrap confidence intervals and McNemar’s exact test on the same lines.

  • Against git’s strongest settings: right on 20 lines where git was wrong, wrong on 2 where git was right (McNemar exact, p < 0.001).
  • Layer C added 7 correct answers and lost none (p = 0.016) — it earns its place in the headline.
  • For the commit where a line first appeared: ours 71.5% vs git’s 51.5%.
  • The development set scored 89.5% — higher than the test set, exactly as expected for the data the method was tuned on. We report both.

Checks that need no labels at all

  • 99.91% of changes we call cosmetic keep Python’s own syntax tree (91.96% under a strict check where import order counts — we report both, since import order is an assumption).
  • Lines landing on a known formatting commit in Django: 22.7% under git’s strongest settings → 1.7% with our automatic lists → 1.2% with the list Django maintains by hand. We also recover 95.7% of the files in Django’s hand-kept list automatically.
  • Per-repo honesty: our skip lists change git’s best answer on 28.6% of Django logic lines but only 0.3% of Redis lines — Redis’s noise is comment edits, not reformats. The gains live where reformats live, and we say so.

Speed and stability: 300 random real lines traced with zero crashes; median 0.03 s, slowest 19.2 s. Reproducibility: uv run python eval/reproduce.py regenerates every number above — verified to reproduce the committed results byte-for-byte.

12What we don’t claim

LimitationWhat we do about it
The gold labels are AI labels; no human has checked them. Claude also built the method.Blind cross-vendor second annotator, frozen held-out test set scored once, everything published for audit — and the caveat stated wherever the numbers appear.
Redis gains little, so “better on every repo” would be false.Results reported per repo; the headline claim is about repos with reformatting history.
Similar “why is this code here” tools exist (why, WhyGraph, Ctxo, Git Archaeologist, Rekal).We claim the evaluated method — per-file cosmetic filtering with measured accuracy against fair baselines — not “the first tool”. They become related work in the paper.
The CI check has low precision in absolute terms: 2.7% of its warnings hit a guard that later had to be restored.That is 3.3× the 0.80% base rate, so the check warns and never blocks, and cites its reason. The next step is recognising rewritten guards and planned deprecations, about a quarter of the false alarms.
The agent result is a pilot: one model, 16 cases, 2 seeds.Reported as a pilot, with every transcript saved; a larger study is the first item of future work.
The synopsis promised a fully local system; Gemini is a cloud API.Flagged to the guide. The LLM sits behind an interface so a local model can return; everything else runs offline.
The explainer is cautious: it answers 19 of 30 questions that have a linked discussion.Of its 11 abstentions, 9 were justified: the discussion described a whole feature, or the line was vendored code. It abstained on all 10 questions whose evidence was withheld.

15Glossary

commit
One recorded change to a codebase, with an author, date and message. Identified by a hash like 8aa71f4e87.
git blame
The git command that names, for every line of a file, the last commit that touched it.
cosmetic change
A change that alters how code looks (formatting, quotes, wrapping) but not what it does.
ignore-revs / skip list
A list of commits git blame should look straight through. Django keeps one by hand; we generate one per file automatically.
token stream
The sequence of meaningful symbols in code, ignoring layout. Identical streams ⇒ identical behaviour.
tree-sitter
A parsing library that turns source code of many languages into syntax trees, tolerating errors.
Trac
Django’s ticket system — where its bug reports and feature discussions live.
FTS5
SQLite’s built-in full-text search engine, used for the local ticket index.
MCP
Model Context Protocol — the standard that lets AI agents discover and call outside tools like ours.
abstention
The system declining to answer when the evidence doesn’t support one, instead of guessing.
gold set
A sample of lines whose true origin was determined independently, used to score every method.
held-out test set
Gold lines drawn after the method was frozen, so they can’t have influenced it. Scored once.
Cohen’s kappa
Agreement between two annotators, corrected for chance. 0.86 is strong agreement.
McNemar’s test
A statistical test for whether two methods’ disagreements on the same items favour one of them beyond luck.
weighted accuracy
Accuracy corrected for deliberate oversampling, so it reflects the real mix of lines.
