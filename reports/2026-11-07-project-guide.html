Provenance-Aware Code Intelligence

What we are building, how it works, what has been done so far and why, and what comes next before the Project-I evaluation on about 21 November.

The short version

  • Goal: before an AI coding agent deletes or weakens a line of code, tell it why that line exists, using the repository's own history.
  • The hard part: finding the commit that really created a line. git blame often points to a reformat or rename instead.
  • What works today: a tracing engine that skips those non-logic changes, a command-line tool, and an MCP server agents can call. It has been run on the full histories of Django and Redis, and 146 tests pass.
  • The biggest unknown: how accurate it is. That needs 60 lines labelled by hand, which is your next job.

Provenance · project guide1 · The problem

1The problem we are solving

AI coding agents change code quickly, and they often "tidy up" lines whose purpose they can't see, such as a check, a retry, a lock or a timeout.

The reason a line exists is usually written down somewhere, in a commit message, a pull request or a bug ticket. The standard way to find it is git blame, which names the last commit that touched each line. That commit is often just a reformat, a rename or a move, which says nothing about why the code is there.

A real example from Django

From django/contrib/auth/hashers.py, which isn't in your annotation sample. The marked line is part of a deliberate type check in make_password().

111        )
112    if not isinstance(password, (bytes, str)):
113        raise TypeError(
114            "Password must be a string or bytes, got %s." % type(password).__qualname__
115        )

Why this matters to an agent

An agent told "Reformatted code with Black" learns nothing, so deleting the check looks harmless. An agent told "Fixed #31375: accept only bytes or strings" knows this is a deliberate guard, so it should keep it or ask first.

The research question for Project-I

Can we automatically find the change that really introduced a line, more accurately than the best git blame setup, and hand that to an agent?

Long-term question: does this actually stop agents making unsafe changes? That's the agent study planned for Phase III.

Provenance · project guide3 · How tracing works

3How line tracing works: three layers

We don't replace git blame. We tell it which commits to skip, then step through the commits it can't skip.

Made-up history for one line, newest on the right:

Layer A · classify

Which file changes kept the behaviour?

For every commit and every file it touched, parse the file before and after with tree-sitter and compare the code tokens. Label each change cosmetic, rename, move or logic.

Runs once per repo: 5.2 min for all 35,104 Django commits.

Layer B · skip

Let git skip those commits

Give git blame a skip list for this file through --ignore-revs-file. Git does the hard line matching, and it's fast and well tested.

Each file gets its own list, so a commit that reformats one file but fixes another is skipped only for the first file.

Layer C · step

Look inside mixed commits

For the one line we care about, look at the commit's diff. If the same tokens were removed nearby, it was only reformatted, so step back. If a similar line was removed, it was edited, so record a logic change and keep going.

Less certain than A, so its confidence scores are lower. Not yet checked against labels.

Two answers per line. The tracer reports the last logic change and the first appearance, because the "why" can live in either. Of 150 random traced Django lines, 33% had been edited after first appearing (23% for Redis), so the two answers often differ.

4Layer A up close: deciding that only the look changed

The idea: turn the code into a stream of meaningful tokens. If the stream is the same before and after, the change can't have altered behaviour.

Before, in 2020
raise TypeError(
    'Password must be a string or bytes, got %s.'
    % type(password).__qualname__
)
After Black, in 2022
raise TypeError(
    "Password must be a string or bytes, got %s." % type(password).__qualname__
)

The quote style changed and two lines became one. The text differs, but the code means the same.

Both versions become the same token stream (simplified)

raiseTypeError("Password must be … %s."%type(password).__qualname__)

Equal streams, so this file change is cosmetic and goes on hashers.py's skip list.

Ignored, because it can't change behaviour

  • Whitespace, line wrapping and blank lines
  • Comments, and docstrings without examples
  • Quote style, string prefixes like u'', and adjacent strings joined
  • Trailing commas and redundant brackets
  • Import order within a block

Kept, because it can

  • Any change to the real tokens
  • Python indentation that moves code into or out of a block
  • Where one statement ends and the next begins
  • Docstrings containing doctests (>>>), since those run as tests
  • Brackets that change what an expression means
LabelRule
renameThe tokens match once names are swapped consistently, and every changed name is defined in that file. That second rule stopped base64.encodestring → b64encode looking like a rename, since that's a different library call.
moveThe same code appears elsewhere unchanged, for example a function moved down the file.
logicAnything else, plus anything we can't parse or don't support.

The safety rule: when unsure, call it logic

The two possible mistakes don't cost the same. Wrongly calling a change cosmetic skips the commit, which can hide a line's true origin. Wrongly calling it logic just gives the same answer git blame would. So unparsable files, unknown languages and unclear cases all count as logic. This is also why the four bugs found so far (section 9) mattered: each one made a real change look cosmetic.

5How an AI agent uses it, through MCP

MCP (Model Context Protocol) is a standard way for AI apps to find and call outside tools. We write one small server, and Claude Code, Cursor and other agents can all use it.

Steps 1 and 6 are an illustration of how an agent should behave. Steps 2–5 are what our server really does.

What the server really returns (shortened)
{
  "status": "traced",
  "file": "django/contrib/auth/hashers.py",
  "line": 114,
  "last_logic_change": {
    "commit": "8aa71f4e87…", "date": "2020-03-31" },
  "first_appearance": {
    "commit": "8aa71f4e87…", "date": "2020-03-31" },
  "chain": [
    { "commit": "9c19aff7c7…", "kind": "cosmetic",
      "confidence": 0.95 },
    { "commit": "8aa71f4e87…", "kind": "origin",
      "confidence": 0.9 } ],
  "commit_messages_untrusted": { … },
  "note": "Missing history doesn't mean a
           change is safe. …"
}
Safety rules built in
  • Read-only. Both tools only read. They can't edit files or run commands.
  • Commit messages are marked untrusted. Anyone can write a commit message, including one that says "ignore your instructions". So messages go in a separate field that is labelled as data.
  • It never says "safe". Finding no history doesn't mean a change is safe, and every answer says so.
  • Paths are checked, so an agent can't use the tool to read outside the repo.
  • It returns evidence, not prose. The calling agent already has a strong LLM, so we don't spend a Gemini call here.

Today it returns trace results and commit messages. PR and issue evidence arrives in Phase II.

7What we have done, step by step, and why

In order, from reading the synopsis to the annotation packet that's now waiting for you.

#What was doneWhy
  1. Read the synopsis and research plan, then checked all four repos through the GitHub API.The plan assumed every repo had PRs and issues on GitHub. PostgreSQL has none, and Django keeps its tickets on Trac, so the design had to change.
  2. Wrote eight plan documents in plans/, from a plain overview to engine details.To settle the design and record decisions before writing code, so nothing gets rebuilt later.
  3. Built ingestion: bare clones, plus every commit and file change in SQLite.Every later step reads from one fast local store, instead of asking git again.
  4. Built Layer A, the tree-sitter classifier, and Layer B, blame with per-file skip lists.The cheapest way to remove most noise. It reuses git's own matching, so our work goes into deciding what to skip.
  5. Compared our automatic skip list with the one Django's developers keep by hand.It's the only real answer key available without hand labelling.
  6. Built an independent check using Python's own parser, and fixed the bugs it found. The rules went through 6 versions.A second opinion that doesn't share our code. It found real cases where we called a logic change cosmetic.
  7. Built Layer C and the "first appearance" answer.Commits that mix a reformat with a real fix can't be skipped whole, so the line has to be followed through the diff.
  8. Built the CLI and the MCP server, and tested the server with a real MCP client as a separate process.This is how an agent uses the tool, and it's the demo for the evaluation.
  9. Ran everything on Redis, and read its flagged commits by hand.C has no parser check like Python's, so reading was the only check available for the second language.
  10. Built the scoring pipeline and a blind 60-line annotation packet. Tested the scorer on fake labels with a known answer.Real accuracy needs human labels. Testing the scorer first means your labelling time won't be wasted on a broken script.
  11. Stress-tested the full tracer on 300 random real lines.To catch crashes and measure speed before the demo. There were no crashes, but one line was too slow.

Where it lives: engine in src/provenance/, evaluation scripts in eval/, results in eval/results/, labelling files in eval/gold/. There are six commits on the project-i-evaluation branch, and nothing has been pushed to GitHub yet.

Similar tools already exist

A web search on 7 Nov found several open-source tools that also answer "why is this code here" from git history, some of them through MCP: why (quangdang46, archived April 2026), WhyGraph, Ctxo and Git Archaeologist. There's also a July 2026 paper, Rekal, that treats git as memory for agents.

What this means for our claim: we can't say we're the first tool that explains code history to agents. None of the tools we looked at showed automatic per-file cosmetic filtering, or any measured accuracy for line tracing. So our difference is an evaluated method that traces lines past non-logic changes, compared against fair baselines. That's only from reading their READMEs, so check their source before the paper.

Provenance · project guide11 · What happens next

11What happens next, and why

Two weeks to the Project-I evaluation. Week 1 is labelling, and week 2 turns the labels into results.

What labelling involves

For each of the 60 lines in eval/gold/packet.md, read the candidate commits and the line's history, then record two answers in annotations.csv:

  1. Which commit last changed this line's logic?
  2. Which commit first introduced it?

If you can't decide, mark the line ambiguous. Those are reported separately, not dropped. The rules are in RULES.md. Expect 2–3 hours.

Why it's done this way

  • Blind: the packet doesn't say which method picked which commit, so your labels can't favour ours. Don't open sample_key.json.
  • A second labeller: their agreement with you (Cohen's kappa) shows the labels aren't just one person's view.
  • Freeze before the final run, so the rules aren't tuned to fit the test lines.
  • Mixed sample: lines were sampled by repo and type, then weighted back, so accuracy isn't skewed.

What the scorer will produce

An accuracy table for every method: plain blame, two stronger git settings, Django's hand list, our Layers A + B, and our full tracer with Layer C. It includes 95% confidence ranges and a statistical test (McNemar) of whether ours beats git's best setting on the same lines. Then we sort every wrong answer into a failure taxonomy, meaning a list of the kinds of mistakes and how often each occurs.
